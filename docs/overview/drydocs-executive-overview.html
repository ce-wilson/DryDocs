DryDocs Don’t Repeat Yourself — Documentation

A governed knowledge graph for DevOps — built around the orchestration record, because that is the only layer that identifies which technical components are actually in use, and the upstream and downstream flows they sit between.

Audience: Leadership · Production Support · Engineering · SME Classification Internal-Public Date 2026-08-07 Revision 8

00 The framing

The name is the thesis, and it has come full circle

Origin — “Full Circle Docs”

DryDocs began as the Python principle applied to documentation: Don’t Repeat Yourself. The working name for the idea was Full Circle Docs, and the problem it was built for is a mismatch of retention.

Agile’s “just enough documentation” produces exactly enough context for the sprint that writes the code, and no more. But a data warehouse retains data for 15 to 30 years. Documentation retention never came close. A decade on, the data is still queried, still regulated, still depended on — and the record of what it is and why it was built that way is gone, along with the people who knew.

The original proposal was a Neo4j graph containing the batch process and the code, linking to the requirements and test cases held in a document database.

Then large language models changed who the reader is. Agents need precisely the thing that was missing: what something is, and why it was done. Documentation written for the auditor turns out to be the context layer the agent needs.

That is the full circle — documentation written once, tied to the code, regenerated on demand, for a reader nobody anticipated.

What that idea became is not one graph but three, separated by how far you can trust what is in them — and separated by the database boundary, not by a confidence field, because a property filter is one forgotten clause away from failing.

A read-only composite (ddall) federates them, so a support question can read across all three while any single write still lands in exactly one. Three words carry the definition of what they add up to:

Graph
The questions are traversals. What breaks if this job fails? Who owns the application behind it? Which product does that roll up to? Those are hops, not joins.
Governed
Every edge means something a human ratified. A relationship type cannot enter the graph without clearing a controlled vocabulary and an SME gate. That is the difference between a knowledge graph and a diagram.
Production support
Cross-product application data flows are not something a runbook captures. Support documentation has slid from robust explanation — an overview, the business context, the process flow — down to the lowest level a developer can deliver: an Excel spreadsheet of Control-M folder and job details. Neither development nor production-support SMEs can do impact analysis or root-cause analysis, on a technical failure or a data defect, without the big picture. The graph supplies it: which failures take precedence, what they touch downstream, and who to notify and engage.

Today it runs self-hosted and single-tenant — a Neo4j graph, a Python pipeline, a read-only API, and a React console, all inside the estate. The shape is deliberately portable: another group could stand up its own graph against its own orchestrator and its own catalog, and those graphs would compose — an ecosystem of graphs rather than one central catalog everyone has to agree on. That is a design property worth protecting, and it is one of the reasons identity and vendor boundaries are being made explicit now.

01 The central design choice

Why orchestration is the backbone

The instinct is to model the business first — segments, products, applications — and hang the technical detail off it. DryDocs does the opposite.

An org chart tells you who is supposed to own an application. The scheduler record tells you what executed — on which server, reading which file, signaling what downstream. One goes stale the moment someone changes teams. The other is rebuilt from the execution record on every ingest.

So the orchestration record is the backbone, and every other layer connects to it: data because jobs read and write files; applications because jobs are associated with one; products and business lines because applications roll up a catalog hierarchy; people because applications carry attributed roles; documents because facts cite the page they came from.

This is the conclusion Databricks Unity Catalog reached independently, for the same reason: lineage derived from what ran stays accurate; lineage declared by a human becomes outdated. DryDocs derives from Control-M definitions what Unity Catalog derives from Spark execution plans.

Which is exactly why the vendor boundary has to be explicit in the code. Control-M is the primary Data & Analytics orchestrator today, and its parser sits in the shared core with no parent and no sibling — while AutoSys is in a later phase, and AWS Airflow is a placeholder with less visibility under tenant-level access restrictions. Both crosswalks are already validated through the SME gate on paper, and neither has anywhere to land in code.

02 What it captures

Five layers, one backbone

The heavy edge — WAS_ASSOCIATED_WITH — is the load-bearing join in the whole graph: where the technical record meets the business record. Its grain (whether attribution attaches at job level or at the folder→batch-port level) is under an open SME gate, and everything downstream of “who owns this failure” depends on how it resolves.

03 What makes the layers joinable

Ontology standards: data, software, organization

A taxonomy tells you what category something is. An ontology tells you what a connection means. Five layers only compose into one graph if the edges between them are drawn from a shared, defined vocabulary — otherwise each source arrives with its own private notion of “owns”, “uses”, and “depends on”, and the graph becomes a picture rather than something you can reason over.

DryDocs does not invent that vocabulary. It maps to W3C and community standards, records every mapping in a controlled registry, and puts the ones that are not yet company-approved behind a fence.

Honest about the gaps

Roughly half the relationship vocabulary maps cleanly onto a standard term. The rest are local domain edges — CONTAINS_JOB, REQUIRES_IN_CONDITION, USES_SOFTWARE — where no standard has a matching row. Those carry an explicit no mapping marker rather than a forced one. Inventing a plausible-looking standard term is worse than declaring the gap, because a wrong mapping is invisible and a declared gap is reviewable.

The same discipline gates promotion. SOSA/SSN is a real W3C standard but not yet a declared company standard, so it is opt-in only, stamped adoption:"experimental" in the graph, and never seeded by the default bootstrap.

Why this is the agent story, not the modeling story

An agent answering “what does this process do, and who do I contact when there is an issue?” has to cross two kinds of evidence: a structured extract that says a job is associated with an application, and prose written somewhere else that explains what that application is for. Nothing joins those but a vocabulary both were mapped into. Where the vocabulary is defined, the agent traverses. Where it is missing, the agent guesses — and guessing is precisely where hallucination enters a support answer.

This is the same conclusion Databricks reached out loud: “agents are only as good as the context they have — without a shared definition of what the business actually means, even a capable agent will guess.” Defining the ontology properly across the taxonomies is not modeling hygiene. It is the difference between an agent that can cite a path and one that produces a confident sentence nobody can verify.

04 How the code is arranged

Modules: who does what

Where people come from

Three feeds populate the people layer, and they are deliberately separate because they answer different questions. The catalog extract supplies teams and the products they support. The application registry extract supplies the operating-model roles attached to each application — who owns it, who informs it, who operates it at each level. The escalation routing feed supplies the group you actually page, which is frequently not the same as the person listed as owner. An HR hierarchy extract — currently at the gate — would add the reporting chain, so an unanswered page can escalate upward rather than sideways.

The trust boundary is structural, not a property

Curated facts and uncertain candidates live in different databases, not behind a confidence field — because one bad query on a shared database promotes noise into ground truth, and a property filter is one forgotten WHERE clause away from failing. Promotion from context to ground truth is a human gate, never a cross-database edit.

05 The configuration layer

Git is the ledger. SQL is the index.

The question behind ADR 0009 was “are these config files getting too big — should this be a database?” The answer is that it already is one, in the half where a database helps.

Four mechanisms make git — not a database — the right ledger, and all four break if the source of truth moves:

1. The SME gate reviews a diff; a domain expert signs off on a readable hunk, not a row delta.  2. The cross-repo port is a commit range, and database state cannot be cherry-picked.  3. Classification is enforced per file — every source declares its sensitivity, which is what keeps internal data out of a published push.  4. Renders are deterministic from committed text, so a stale render is detectable by re-rendering and diffing.

What a database does give — fast, joinable, ad-hoc query — is already delivered by the derived SQLite model, deletable at any moment without data loss. The genuine gap is the arrow marked promote: a console that edits governed configuration needs somewhere durable to keep an unfinished edit. That is the piece to build before the console grows more write surfaces.

06 Capture → document → feedback → remediation

The loop that makes it a system, not an inventory

The documentation cycle4 → 5 → 6 → 4

Markdown is the source; the HTML render is deterministic; the printed sheet and the browser page carry the same anchors. An SME can mark up paper with a pen, scan it, and the transcription lands as anchor-keyed YAML that re-attaches to the exact section it annotated. This is why governed renders must be shared exactly as rendered — a “prettier” copy silently breaks re-attachment. It is also Full Circle Docs in its literal form: the document is regenerated from the graph, corrected by a human, and the correction goes back to the source rather than into a side file.

The original proposal is not backstory here — it is live vocabulary. The batch process and the code are in the graph; SPECIFIED_IN links a requirement to the document section that states it, VERIFIED_BY links it to the test case that proves it, and IMPLEMENTED_BY links it to the component that satisfies it. All three are active edges today. The document-database half — the corpus those sections live in — is dddocs, decided and pending build; it is the last dotted line in this particular circle. The design drawn for a fifteen-year audit trail and the design an agent needs to answer a question turned out to be the same design.

The remediation cycle3 → 7 → 8 → 9 → 1

Defects are detected against the graph, a corrected definition is authored offline, and — the critical step — proved equivalent before anyone sees it: does the fixed definition re-derive the same resolved behavior? Only then does it become a Jira. Remediation writes no graph and deploys nothing; Jira is the system of record and the dev team holds deploy rights. The proof closes when the next ingest re-derives reality and confirms the fix landed.

The trust cycle3b → context → gate → graph

Anything the system inferred but cannot stand behind goes to a separate database and stays there until a human promotes it.

The property that makes all three work is the one from the top of this page: capture is a byproduct of what ran, not a documentation chore. Every loop re-grounds on the next ingest, so the graph corrects itself rather than drifting.

Target state: only actively used code on the production server

The goal is a production estate that holds only code that is actually used. When a script has been fully replaced, it belongs in version control and archive storage — not left on the server, where the next person on call has to work out whether it still matters. This is a target the loops above move toward, not a description of today.

The graph makes it measurable because it keeps three signals apart instead of collapsing them into a single “used” flag: what is deployed on a server, what is called by a job, and what a pipeline registry still lists as active. A script that is present and called by nothing is a candidate for review. Archived code is the same question answered from the other side — still in the repository, no longer on the server — so progress toward the target is a number the system can report, not an impression.

The limit is coverage, and the report states it rather than leaving it to the reader. Each of the three signals can only show presence, and each is bounded by what its feed actually scanned. Calls from one script to another are visible only where the collector carried the script body, so on a listing-only capture “unreferenced” means no command-line reference was observed — never nothing calls it. An absence recorded by one feed is not an absence in the estate.

That is why the system proposes and a person decides. The report separates three outcomes rather than two: code that is genuinely dead and can be archived and removed, code that was deployed to the wrong server and should be relocated instead of deleted, and code no command line names but a captured script body does call. Merging those three would turn a cleanup into an outage, which is the same reason nothing here deletes on its own judgement.
