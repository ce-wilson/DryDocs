### 1. The D2 loader-source overlay makes require_confirmed refuse a built loader, and the wiring guard can never see it

`drydocs/cli_shared.py:830` · **medium** · correctness · dimension `wired-axis`

**Claim.** _gate_loader gates the EFFECTIVE dataset id (the D2 overlay's target), but the guard that holds the wired declaration honest reads CLASS-DEFAULT bindings. With any overlay entry the two cannot both be satisfied: declare the effective id wired:true and test_wired_declaration_agrees_with_the_tree fails; declare it false and require_confirmed raises UnwiredSourceError for a loader that is built and was loading before CFG13. This is the one path where the axis does change a row's load state, contrary to the D1 ruling the build cites.

**Evidence.** cli_shared.py:830 `effective = _source_registry().effective_source_id(cls.name, cls.source_id)` then `_gate_source(effective)`. tests/unit/test_source_descriptors.py:155-157 `bound = {cls.source_id for cls in cli.LOADER_REGISTRY.values() ...}` — class defaults, never effective_source_id. Reproduced at this commit with a one-entry overlay (config/loader-source-overlay.yaml's documented company shape): overlay {controlm_folders.v1: "controlm@[db].psgmgr.cm_def_setvar_vw"} -> effective id = cm_def_setvar_vw -> reg.require_confirmed(eff) raises UnwiredSourceError "confirmed but NOT WIRED"; and `eff in bound` is False, so the guard requires that id to stay declared false.

**Failure scenario.** Company side, where the overlay exists for "the ~8 mismatched + ~13 unbound company loaders" (config/loader-source-overlay.yaml header): a loader whose overlay target is a confirmed dataset ran fine before CFG13. After the port, `drydocs load <loader>` prints the red UnwiredSourceError and exits 2. Flipping that id to wired:true to fix it reddens test_source_descriptors.py instead, because the guard only looks at class defaults. Producer-side this is latent only because the shipped overlay is empty — which is the one condition the mechanism exists to stop being true.

**Suggested fix.** Build the guard's `bound` set through registry.effective_source_id(cls.name, cls.source_id) (the same call the gate makes), and render the load-map `loaders` array off the effective id too, so declaration, gate and surface all key on the id that actually loads.

### 2. Intake write handlers commit before the only ownership check, so a cross-persona mutation lands and the 403 is cosmetic

`drydocs_api/intake.py:823` · **medium** · security · dimension `api-surface`

**Claim.** `transition`, `thread_decision` and `add_evidence` authorize by ROLE only (`_authorize` just resolves the token). The per-record ownership rule — `session.role == "user" and record["created_by"] != session.persona_id` — exists in exactly one place, `get_intake` (line 636), which these three handlers call as their RETURN VALUE, after `store.conn.commit()`. So a user-tier persona can drive another persona's intake through the status machine, terminate it as `no-new-value`, or write an evidence file into its directory; the write is durable and the caller then receives a 403. The read side (`get_intake`, `list_intakes`) enforces ownership; the write side does not.

**Evidence.** intake.py:823-824  `store.conn.commit()` / `return get_intake(intake_id, token, sessions, store)` (same shape at 546-547 in add_evidence and 854-855 in thread_decision); the only owner test is intake.py:636 `if session.role == "user" and record["created_by"] != session.persona_id: raise Forbidden(...)`. TRANSITIONS (intake.py:82-101) gives `_ANY = ("user","steward","admin")` every non-admin edge.

**Failure scenario.** Executed against this commit with the framework-free handlers: `neo` (role user) creates an intake -> id `1d07ccf0210b`, status `draft`. `mouse` (role user, different persona) calls `transition(iid, "ontology-reviewed", "", mouse.token, ...)`. Output: `transition raised Forbidden: users see their own intakes; the queue is steward/admin` — and `STATUS AFTER THE 403: ontology-reviewed`, with the event log reading `[('neo','created'), ('mouse','transition:draft->ontology-reviewed')]`. The same call for `add_evidence(iid, "x.txt", b"...")` raises Forbidden and still leaves `x.txt` on disk under neo's intake directory plus a committed evidence row. A user-tier persona learns another persona's intake id without the queue: `_check_thread` writes matched prior intake ids into `thread_of_json` (intake.py:600-607) and `_serialize` publishes them as `thread_of` (intake.py:385).

**Suggested fix.** Move the ownership test out of `get_intake` into a shared `_authorize_record(session, record)` called immediately after `store._record(intake_id)` in `add_evidence`, `transition` and `thread_decision` — i.e. before any write, not as the return value. `get_intake` keeps its own check for the read path.

All three `store.conn.commit()` and then `return get_intake(...)`, and line 636 is the sole `created_by != session.persona_id` test. The wiring is live: `drydocs_api/app.py:771-826` exposes all four writes behind plain `CurrentUser` (no `require_role`), and `_intake_call` maps `Forbidden` to HTTP 403 (740-741) with no rollback.

### 3. The display `limit` param is unbounded in both directions: an arbitrary int is buffered into memory, a negative one reaches the driver

`drydocs_api/queries.py:97` · **medium** · correctness · dimension `api-surface`

**Claim.** `DEFAULT_DISPLAY_LIMIT = 500` is a DEFAULT, not a bound. `validate_params` type-checks `limit` as `int` and applies no range, so any authenticated caller sets it to any integer. `execute_spec` then does `rows = list(rows)` (exports.py:319), buffering the whole result before slicing. This contradicts the invariant exports.py:48-58 states when justifying `EXPORT_LIMIT_CEILING`: "The display ceiling (500) bounds a GRID... An unbounded export over a result set nobody has counted is the failure the display limit was protecting against". The export path refuses 10,000,000; the read path the ceiling is said to rest on accepts it.

**Evidence.** queries.py:97 `"int": lambda v: isinstance(v, int) and not isinstance(v, bool)` — the only check; queries.py:108-129 `validate_params` has no range logic, and `ParamSpec` (queries.py:14-19) carries no min/max. exports.py:319 `rows = list(rows)`. exports.py:247-252 shows the contrast: `resolve_export_limit` does bound the EXPORT request.

**Failure scenario.** Executed at this commit with a fake runner: `run_spec("docs.email-unassigned.v1", {"limit": 10_000_000}, ...)` returns `limit -> 10000000` and the driver receives `{'limit': 10000001}`; `resolve_export_limit(spec, {...}, 10_000_000)` on the same spec raises `export limit 10000000 exceeds the server ceiling 50000`. Against a live graph the first call materializes up to 10M records in the API process. Second mode, same root: `run_spec(..., {"limit": -5}, ...)` passes validation and the driver receives `LIMIT -4`, which Neo4j rejects with a ClientError; `post_spec_run` (app.py:627-649) catches only InvalidTokenError / UnknownSpecError / ParamValidationError, so the client input surfaces as an unhandled 500 rather than a 422. With a runner that returns rows, `truncated = limit is not None and len(rows) > limit` (exports.py:320) is also True for any negative limit and `rows[:limit]` silently drops the last |limit| rows — a false statement in the one field API1 exists to make honest.

**Suggested fix.** Give `ParamSpec` a range (or special-case `DISPLAY_LIMIT_PARAM` in `validate_params`): reject `limit < 1` and clamp/refuse above a named `DISPLAY_LIMIT_CEILING`, the way `resolve_export_limit` already refuses rather than silently clamping.

**What the verifier established.** Premise verified line by line at f99219e0. queries.py:95-98 is exactly the int/bool check quoted; validate_params (108-129) enforces unknown-key, required, type and default and applies no range; ParamSpec (14-19) has no min/max. DEFAULT_DISPLAY_LIMIT = 500 is a ParamSpec DEFAULT (query_specs.py:136-138), not a bound. exports.py:319 is `rows = list(rows)`, 48-58 carries the quoted EXPORT_LIMIT_CEILING rationale verbatim, resolve_export_limit (221-254) does bound the export. QueryBody.params is a bare dict (app.py:146-147) and post_spec_run catches only InvalidTokenError / UnknownSpecError / ParamValidationError, so a driver ClientError surfaces as 500. LiveRunner.run uses execute_query (app.py:230-250), i.e. fully buffered, so the read path really does materialize before slicing. Reproduced both modes with a fake runner and a real persona token: {"limit": 10_000_000} is accepted, reported as limit 10000000, driver receives 10000001, while resolve_export_limit on the same spec raises "export limit 10000000 exceeds the server ceiling 50000"; {"limit": -5} is accepted, driver receives -4, and with a runner that returns rows truncated is True and 5 of 10 rows are silently dropped. No guard exists: test_drydocs_api.py:139-150 covers missing/unknown/wrong-type/bool and deliberately not range; test_query_specs.py:340 covers unknown params only; test_result_completeness.py:271-281 bounds the EXPORT limit (0, -5, "500" refused) and never the run limit. Not ruled deliberate: a caller-supplied run limit is intended (test_a_caller_raised_run_limit_is_the_ceiling_that_is_reported, line 173) and app.py:151-161 explains why export has its own ceiling, but nothing states the run range is unbounded on purpose, and the adjacent recorded candidate in docs/reviews/modules/api-2026-09-08.md ("Decide a query bound", never minted) is about query TIME, not parameter range. Downgraded from high to medium: it needs an authenticated session and crosses no authz boundary (Cypher is spec-fixed, params are bound parameters); the buffered read is bounded by the spec's actual result set rather than by the requested 10M; and the silent-row-drop mode needs a runner that returns rows, since real Neo4j rejects LIMIT -4, so production sees an unmapped 500 — the same unmapped-exception shape that report's own L1-1 already records. What survives is a one-line input-validation gap with a genuine asymmetry against resolve_export_limit, plus a `truncated` value that can be false for a negative limit, in the one field API1 exists to make honest.

### 4. The proxy-prefix absence scan can never fail: its subject exists only inside string literals, which the stripper blanks

**Claim.** test_the_proxy_path_map_is_read_from_delivery_json_and_not_restated searches the JS-stripped renderer for '/api' and '/agent'. This scan was vacuous from the day it was written").

**Evidence.** tests/unit/test_compose_stack.py:151-154 — `code = _js_code_only(RENDERER.read_text(...))` then `restated = [p for p in ("/api", "/agent") if p in code]` / `assert not restated`. _js_code_only (line 82-94) runs `re.sub(rf"{quote}(?:\\.|[^{quote}\\])*{quote}", '\"\"', out, ...)` for `'`, `"` and backtick. Measured against deploy/render_proxy_config.mjs at this commit: delivery in code: True; '/api' in code: False; '/agent' in code: False. Whichever form, give it a positive control (tests/source_scan.py's `absent(..., positive_control=...)` is the repo's own answer; a JS-side equivalent needs the same).
