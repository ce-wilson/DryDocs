### 3. The PORT4 drop check builds its drop set with `git diff --name-only --diff-filter=D`, which git's default rename detection silently empties for any drop paired with a similar add — so a renamed-away file reads as "no drop", and a correct accepted_drops ruling for it is reported as STALE.

**Severity:** high · **Where:** `drydocs/port/port_drops.py:251` · **Dimension:** port-and-libs

**Failure scenario.** The consumer applies a canonical-producer take that renames a file it already holds (the real shape port_rename_detect.py exists for: `41-local-seal.yaml` -> `41-local-business-application.yaml`, git-scored R095). At the close, `port_drop_check <pre-port-tag>` runs `git diff --name-only --diff-filter=D <pre-port-tag> HEAD`, git classifies the pair R (not D) because diff.renames defaults to true, so `git_dropped_paths` returns a set with no `41-local-seal.yaml` in it. `check_drops` gets `dropped_set` without the path and `present_set` without it either, so the report prints "dropped, unruled: none / RESULT: PASS" for a file that is gone — the exact silence PORT4's docstring says the seam exists to eliminate. Worse in the ruled case: if the consumer HAS written an `accepted_drops:` row for that path, the `elif path not in dropped_set` branch (line 241) files it under `stale` with "nothing dropped this path — the row describes no drop", the report FAILS, and it instructs the operator to retire a ruling that is correct.

**Evidence.** Read drydocs/port/port_drops.py in full. Line 249-254 `git_dropped_paths` docstring claims "Paths tracked at ``since`` and not at HEAD — the cumulative drop set", but line 251 passes no `--no-renames`.
