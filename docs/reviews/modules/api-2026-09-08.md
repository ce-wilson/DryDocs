## Lens 1 — system design

**This module has the best contract discipline in the sweep so far, and it has already
SOLVED the root cause the previous three slots each found.** Its one consequential gap is
that a correct behaviour it implements in exactly one place is not applied at the seam
where users meet it.

### L1-1 — a graph outage reaches the console as a 500, which the console is built not to recognize

`drydocs_api` catches a driver failure in **exactly one endpoint**, and does it well
(`app.py:480-490`): the graph-status route runs `RETURN 1 AS ok`, catches `Exception`,
and returns `GraphStatusOut(reachable=False, detail=type(exc).__name__)` — **the class,
never the message**, because a driver message quotes the URI it dialled and a page must
carry no host or port (ADR 0020). The comment even records that a wrong `NEO4J_URI`
first throws there rather than at server start, and that this is *"a reachable=false, not
a 500."*

**No other route does this.** Verified across the module: `ServiceUnavailable`, `503` and
`SessionExpired` appear **nowhere** in `drydocs_api/`, and there is no
`app.exception_handler` mapping driver classes to a status. So when Neo4j is down while
drydocs-api is up, `/specs/{spec_id}/run` — the workhorse behind every console grid —
propagates the driver exception and FastAPI answers **500**.

**Why that specific number matters.** The console decides "the service behind this path
is down" with `isUpstreamDown` (`web/src/lib/reachability.ts:45-47`), which is exactly
`502 || 503 || 504`. **500 is not in the set.** So during a graph outage every data page
renders a generic failure rather than "the graph is unreachable", while the one surface
that *could* say so is a separate probe the page may not have called. A support engineer
then debugs the console, or the API, for a database outage.

**Cheapest correction, and it is genuinely cheap:** one FastAPI exception handler mapping
the driver's error classes to **503**. No console change is needed — `isUpstreamDown`
already treats 503 correctly, and the reachability copy already exists. The one care
point is the same one `app.py:484` already names: pass the exception CLASS, never its
message, or the handler leaks the URI that ADR 0020 keeps out of the page.

### L1-2 — nothing in the module bounds how long a query may run

`timeout` appears nowhere in `drydocs_api/` outside `app.py`, and no spec, runner or
route sets one. The lens asks whether loading is distinguishable from hung; here it is
not, and there is no cancel and no retry. With 48 registered specs over a graph whose
`controlm_variables` extract documents a ~240k-row table, a heavy or pathological spec
holds the request until something upstream gives up — and what gives up first is the
proxy, which returns 504, which the console *does* read as "service down". So the
failure mode is: a slow query is reported to the user as a dead service.

Lower-ranked than L1-1 because it needs a decision (what ceiling is right, and per-spec
or global) rather than a handler, and because it degrades to a message that is at least
in the right family.

### L1-3 — what this module already gets right, recorded so no later firing re-audits it

**Completeness is DECLARED, and the consumer READS it.** This is the direct answer to the
root cause slots 9, 2 and 3 each found from a different side. `schemas.py:254` — *"API1
(d): completeness, declared. `truncated` says the spec's ceiling cut…"* — and the flag is
on the response, with `DEFAULT_DISPLAY_LIMIT = 500` as a named, tunable ceiling
(`query_specs.py:136`). The console consumes it rather than inferring it:
`web/src/explorer/SpecGrid.tsx:33` states *"COMPLETENESS IS READ, NEVER INFERRED"*, there
is a dedicated `TruncationBadge`, and `SpecGraphPane` passes `rowsTruncated`. **A working
remedy for the sweep's recurring finding exists in this repo, end to end, today.**

**The audit covers exactly the routes that change state — no more, no less.** 14 audited
routes. I checked the apparent gap and it is not one: `/mappings/changeset` is the only
mapping POST without an `audit_route`, and it is also the only one that performs no store
write — the three `mapping_store` mutations (`add_draft` ×2, `set_draft_status`) sit in
`/mappings/overrides/draft`, `/mappings/app-code/draft` and
`/mappings/drafts/{id}/promote`, all three audited. The audit is split by kind, too:
`api` never carries Cypher text or result values (an access record, not a data copy),
while `api-debug` does and is enabled settings-level so *"a per-request header would let
an untrusted caller turn on verbose capture of their own traffic"* (`audit.py:1-18`).

**Ephemeral specs are bounded on every axis that can leak.** Agent-key gated so a browser
bearer can never register Cypher, hash-addressed so the ref commits to what runs,
session-scoped with a 404 that does not leak existence, and both TTL- and
capacity-bounded with oldest-first eviction (`ephemeral_specs.py:1-30`). This is the
mechanism that lets `/raw-cypher` stay admin-gated rather than being loosened.

### The pattern other slots should copy: a cross-cutting guard that is DERIVED, not repeated

`query_specs.py` carries **71 hand-written `NOT x:SchemaMeta` guards** across 48 specs.
That looks like the repo's recurring duplication shape and is not, because the second
guard is generated from the first:

`_with_ground_truth_exclusion` (`query_specs.py:150`) runs at **registry build** and
rewrites every `NOT x:SchemaMeta` into `NOT x:SchemaMeta AND NOT x:Uncertain`, exempting
specs that declare `uncertain=True`. Its docstring names the alternative and rejects it —
*"Hand-editing ~30 queries is the exact failure the clause names"* — and
`tests/unit/test_uncertain_boundary.py` proves the transform landed on every ground-truth
spec and that none mentions `:Uncertain` any other way.

So one cross-cutting predicate is written by hand (and forced by
`test_schema_meta_exclusion` on every bound label var), and a second is derived from it
mechanically at build time. Adding a spec cannot forget the `:Uncertain` half, because no
one writes that half.

**Why this belongs in a tech-debt lens rather than a design one:** it is the exact
counter-example to slot 2's L2-2, where `catalog.py` repeats 11 two-line validator
wrappers around a helper defined in the same file. Same repo, same problem shape, two
outcomes — one derived at build, one retyped per class. If slot 10 wants a concrete
remedy to point at when it reports the duplication pattern, it is here.

### The three candidates that were checked and cut

1. **`query_specs.py` is 1,921 lines, 21% of the module.** Cut: it is a declarative
   registry of 48 specs at roughly 40 lines each (cypher, columns, description,
   classification), and its one piece of behaviour is the derived guard above. Size is
   not debt when the file is a table; a finding needs a consequence and this one has none
   that I can write down.
2. **`/mappings/changeset` is the only mapping POST with no `audit_route`.** Cut: it is
   also the only one that performs no store write — the three `mapping_store` mutations
   sit in the three audited routes. The audit covers exactly what changes state. (Detail
   in Lens 1's L1-3, because the checking belonged there.)
3. **The 71 repeated `:SchemaMeta` guards.** Cut: duplication with a test forcing it is a
   caught failure mode, not a latent one, and deriving the first guard as well would mean
   parsing every spec's bound variables at build time to decide where it belongs — more
   machinery than the failure justifies.

## Ranked

Two findings, both from Lens 1; Lens 2 returned none that meet the bar. Both are failure
behaviour, and neither is a defect in what the module does when things work.

1. **L1-1 — a graph outage answers 500, and the console reads only 502/503/504 as
   "service down".** The module catches driver failure correctly in exactly one endpoint
   (`app.py:480-490`) and nowhere else; `ServiceUnavailable`/`503` appear nowhere in
   `drydocs_api/`. Ranked first because it is a one-handler fix with a real operational
   cost today: during a Neo4j outage every console data page shows a generic error, so
   the first hour of an incident is spent debugging the console or the API for a database
   problem. The console needs no change — `isUpstreamDown` already handles 503.
2. **L1-2 — no query bound anywhere in the module.** `timeout` is set by no spec, runner
   or route, so hung is indistinguishable from slow, there is no cancel and no retry, and
   the first thing to give up is the proxy — which returns 504, reporting a slow query to
   the user as a dead service. Ranked second because the fix is a decision (what ceiling,
   global or per spec) rather than a handler, and because its wrong answer at least lands
   in the right family.

**Not ranked:** everything in L1-3 and Lens 2 — the declared-and-consumed truncation
contract, the audit that covers exactly the state-changing routes, the bounded ephemeral
spec store, and the derived `:Uncertain` guard. Recorded so no later firing re-audits
them.

## Cross-links

**Between the lenses.** They agree, and unusually the design lens found the weaker
result: Lens 2 found essentially nothing to report across 9,153 lines, while Lens 1 found
two failure-behaviour gaps. Both findings share a shape with each other and with the rest
of the sweep — **the module is careful about what it says and silent about what it cannot
do.**

**To slots 9, 2 and 3 — the recurring root cause has a remedy, and it lives here.** Web
found a console that truncated silently, load found a `:JobRun` that records no scope,
lineage found a counted tier with no writer: three slots, one shape, *a number that means
two things and says only one*. **This slot is the fourth instance and the first fixed
one.** `schemas.py:254` declares `truncated` on the response, `DEFAULT_DISPLAY_LIMIT` is
a named ceiling, and `SpecGrid.tsx:33` states *"COMPLETENESS IS READ, NEVER INFERRED"*.
The pattern is: **the producer declares the limit of its own answer, and the consumer
renders that declaration rather than inferring it.** Slot 10 should carry that forward as
a remedy the repo already owns, not a proposal — load's L1-1 and lineage's L1-1 are both
this same fix applied one layer down.

**To slot 2's L2-2 specifically.** `catalog.py` retypes 11 validator wrappers around a
helper in the same file; `query_specs.py` derives its cross-cutting guard at registry
build and proves the transform with a test. Same repo, same problem, two outcomes. When
slot 10 reports the duplication pattern it has a working answer to point at.

**Forward to slot 10.** Two questions this slot raises that only the seams slot can
settle: whether the declared-completeness contract should be a repo-wide expectation
rather than one component's good habit; and whether "what does a caller see when a
dependency is down" has a single answer anywhere, given the console defines it as
502/503/504 and only one API route knows to say so.

## Candidates for grooming

Four. None minted — the backlog pen is Lane A's and this firing holds neither it nor an
id.

1. **Map driver failures to 503.** `drydocs-api`, p2, and the cheapest high-value item in
   this report. One FastAPI exception handler over the Neo4j driver's error classes; the
   console already treats 503 correctly and needs no change. **Carry `app.py:484`'s rule
   into the acceptance:** the handler passes the exception CLASS, never its message, or
   it leaks the URI ADR 0020 keeps out of the page. A guard belongs with it — nothing
   today would notice this regressing.
2. **Decide a query bound.** `drydocs-api`. A decision before a build: global or
   per-spec, what ceiling, and what the caller is told when it trips (which should be
   distinguishable from "service down", or it recreates finding 1 by another route).
3. **Consider making declared completeness a repo expectation.** Cross-module, and
   probably slot 10's to frame. This module and the console already implement it; load
   and lineage each have an open finding that is the same contract missing. The item is
   "decide whether this is a convention", not "build it again".
4. **Nothing for `query_specs.py`'s size.** Recorded deliberately as a non-candidate: at
   1,921 lines it is the largest file in the slot and it is a declarative table with one
   piece of derived behaviour. A later firing that wants to split it should first write
   down what goes wrong today, because this firing could not.
