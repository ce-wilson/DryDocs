## Lens 0 — architecture (`/architecture`)

### Verdict

The console has a real architecture, not an accreted one. The ADR 0005 GraphAccess
seam is genuine and enforced by construction. Eight structural issues sit on top of
it, three of which are single-source-of-truth violations where a governing
abstraction exists and the call sites route around it.

### What holds

- **The GraphAccess seam (ADR 0005).** src/lib/graph.ts is the only graph read
  path. Two adapters: bolt (dev bench) and api (deployment). boltAllowed() gates on
  import.meta.env.DEV, a build-time constant, so production bundles have the bolt
  path unreachable by construction rather than by runtime flag. The bolt adapter
  fails loud on runNamed/runSpec/exportSpec rather than forking the query
  definitions client-side. ADR 0005 is ACCEPTED and the code matches it.
- **The generated-client bet (O70).** openapi-fetch over the drydocs_api OpenAPI
  schema. api.d.ts is type-only, zero bundle cost. The chain
  drydocs_api to openapi.json to api.d.ts is drift-tested at both ends
  (tests/unit/test_openapi_client.py, web/src/generated/api.test.ts).
- **Generated-artifact discipline.** Nine artifacts, each with a named Python
  renderer and a regenerate-and-compare pytest guard. Strongest pattern here.
- **Session handling.** Token-only in localStorage, role re-derived from PERSONAS
  and re-resolved server-side, one 401 anywhere ends the session everywhere via a
  window event. The secret is never stored.
- **CI covers web properly.** A separate web job runs oxlint, tsc -b plus vite
  build, vitest, and Playwright with trace upload on failure. Blocking.
- **Hygiene.** dist/, test-results/ and .env.local are all untracked.
  .env.example carries the ADR 0005 warning about VITE_ inlining.

### A1 — Authorization policy has two independent expressions

src/modules/registry.ts declares access per module and canAccessModule() is the
stated single check. It drives the nav (layout/Aside.tsx), the Overview spokes
(routes/OverviewRoute.tsx) and the canvas host gate (routes/GraphCanvasRoute.tsx).

The route table in src/App.tsx does not use it. It restates the predicate
persona.role === 'steward' || persona.role === 'admin' inline six times, for
remediation, software, gates, load-map, under-the-hood and mappings.

The comment on the remediation route records that this exact divergence already
shipped once. O59 set that module's registry access to 'sme', which hid the nav
entry and left the route reachable by typing the URL. The fix chosen was to
duplicate the predicate at the route rather than derive the route gate from the
registry. The next module added with access 'sme' and no hand-written route gate
reproduces the same bug.

Recommendation: App.tsx derives each gate from MODULES via canAccessModule, plus a
vitest asserting every module id with a non-'all' access has a gated route. This is
ADR-sized only because /intake gates on a persona id and /console on a role, and
the current access union cannot express both.

### A2 — A second HTTP stack bypasses the typed client

src/lib/adk.ts talks raw globalThis.fetch to the ADK agent server on port 8000. It
is untyped, has its own asJson error handling, and has no OpenAPI schema behind it.
Its consumers are src/ask/askApi.ts (the Ask route) and
components/CypherConsole.tsx.

So the O70 guarantee, that a server change the console has not caught up with is a
tsc error, covers drydocs-api and does not cover the agent tier. The two surfaces
outside the guarantee are the two agentic ones, whose contracts are the least
stable.

Also, askApi.ts sits in src/ask while every other API wrapper is in src/lib.

### A3 — TypeScript strict is off

Neither tsconfig.app.json nor tsconfig.node.json sets strict, strictNullChecks or
noImplicitAny. The Vite React-TS template ships strict true, so this was removed or
written out deliberately at some point.

This weakens A2's counterpart directly. The generated api.d.ts models optional
fields as optional, and without strictNullChecks the compiler does not enforce
them. The architecture's central claim about compile-time API safety is only
partly cashed.

The four linting flags that are set (noUnusedLocals, noUnusedParameters,
erasableSyntaxOnly, noFallthroughCasesInSwitch) are cosmetic next to this.

### A4 — Role-gated routes ship their payload to every role

There is no code splitting. vite.config.ts is three lines with no manualChunks, and
there is no React.lazy or dynamic import anywhere in src/. The build is one
3,676,794-byte index chunk.

Every generated artifact is a static import, so all of them sit in that chunk for
every signed-in persona.

| artifact | raw KB | route that uses it | route gate |
|---|---|---|---|
| enforcement-matrix.json | 275 | /admin/config | admin only |
| world-map.ts | 147 | /explorer Locations tab | all |
| load-map.json | 56 | /load-map, lineage, software | steward+admin |
| gates.json | 44 | /gates | steward+admin |
| remediation-profile.json | 16 | /remediation | steward+admin |
| software-registry.json | 13 | /software | steward+admin |
| gazetteer.json | 7 | map resolve | all |
| remediation-diff.json | 6 | /remediation | steward+admin |
| context-types.json | 1 | /intake | SME persona |

About 565 KB raw, roughly 15% of the chunk. Around 410 KB of it belongs to routes a
user-role persona can never open.

The route gate is a render decision, not a delivery decision. A user-tier persona
downloads the full enforcement matrix and the gate record and can read both from
devtools. The server correctly enforces API calls, but these artifacts never cross
the API. Whether that matters depends on the classification of those artifacts,
which is a publish-boundary question worth an explicit answer rather than an
assumption.

Cheapest fix: React.lazy on AdminConfigRoute and the Locations tab moves about
420 KB out of the initial chunk and out of every non-admin browser, with no change
to the generation pipeline.

### A5 — The synthetic-data fallback is unowned policy

Eleven demo modules ship in src/: demoGraph, demoLineage, demoLoads, demoOwnership,
demoProductRollup, demoRemediation, demoRunbooks, demoDocs, demoSwimlane,
demoStatus, mappingsDemo.

At least five routes implement try-live-else-synthetic and each expresses it
differently. SpecGrid and LoadsRoute swallow the failure and substitute demo rows
behind a badge. SpecGraphPane and CorpusStatus refuse to render. OverviewRoute
catches and discards the error deliberately to avoid a false green. MappingsRoute
keeps a separate apiDown string. Empty-result and request-failed are the same
condition in some and different in others.

This is the finding I rank first. The DryDocs product thesis is provenance and
trust. The console carries a TrustLegend component, SYNTHESIZED watermarks and
classification banners on spec results. Yet the single most important trust signal,
whether the numbers on screen came from the graph or from a constant in the bundle,
is decided ad hoc in five places with five different presentations. A module that
degrades to demo data without saying so clearly is the exact failure the rest of
the provenance machinery exists to prevent.

Recommendation: one useLiveOrDemo seam returning a discriminated union of
live | empty | demo | error, and one presentational component rendering the
provenance state. Make it the only way a route may reach a demo module, and guard
that with a source scan the way the parent repo guards render parsing.

### A6 — No data layer; routes are coupled to transport

Consequence of A5 and visible on its own.

- The literal (import.meta.env.VITE_API_URL as string | undefined) ?? the localhost
  8001 default appears verbatim in 12 files. apiBaseUrl() in src/lib/auth.ts
  already does this and three call sites use it.
- useMemo(() => createApiAccess(apiUrl, persona.id), [apiUrl, persona.id]) appears
  in 14 files.
- The same cancelled-flag async effect is hand-rolled in 12 files, plus two more in
  event handlers.
- No react-query, no store, no reducer. One React context, and it is UI chrome
  (rightSidebarContext). Cross-cutting state lives in localStorage with a
  hand-written read, parse and guard at six or more separate keys.

Loading is modelled everywhere as data-is-still-null, so no route can distinguish
loading from loaded-empty without an extra boolean. LoadsRoute already carries one
for exactly this reason.

### A7 — Test topology is inverted

12 test files across about 147 source files. Six are in src/lib, two in
src/remediation, one each in components/map, generated, lineage and modules. Zero
in src/routes.

The untested files are the large ones: AppCodeCascadePane at 931 lines,
MappingsRoute at 577, AskRoute at 503, LoadMapRoute at 501, IntakeRoute at 491. The
e2e suite is 75 lines and two tests, sign-in success and sign-in refusal.

The CI comment on the web job says the console had no automated test of any kind
until that job existed, and that two defects reached main and were caught by a
person looking at the page. The job now exists. The coverage behind it is still
concentrated away from where the complexity is.

### A8 — README contradicts the code on the security model

web/README.md is 265 lines and materially wrong in four places.

1. It says there is no ?as= parameter. App.tsx has one. It is DEV-only and now
   requires VITE_DEV_CONSOLE_SECRET, which is a defensible design, but a reader
   auditing auth from the README concludes the affordance was removed.
2. It says 9 module routes and 9 site-plan modules. registry.ts declares 12.
3. It says all 9 modules are open to every signed-in persona and only /console is
   role-gated. Five modules carry access 'sme', and App.tsx gates six routes plus
   /console, /admin/config and /intake.
4. The persona table lists three personas as J. Doe, A. Smith and K. Chen. auth.ts
   has six personas, and its header records that the SID-shaped identities were
   retired on 2026-08-28 for publish-boundary reasons. The README carries the
   retired names forward.

Point 3 is the one that matters. A doc understating the authorization surface is
worse than no doc, and it is the doc a company-side reader reaches first.

### Structural placement notes (carried to pass 3)

- src/docs/ and src/docsmod/ hold one file each. Two directories, one concern.
- routes/ holds non-route components. AppCodeCascadePane is 931 lines and used only
  by MappingsRoute. DomainGridTable is used by MappingsRoute and ui/tableControls.
  Every other feature has its own directory.
- src/data/ holds mappingsDemo.ts while every other demo module lives in its
  feature directory.

### Ranked

1. A5 synthetic-data fallback is unowned policy (contradicts the product thesis)
2. A1 authorization has two expressions (already caused one shipped bug)
3. A3 strict off (undercuts the O70 architecture)
4. A4 gated payloads ship to every role (delivery plus boundary question)
5. A2 untyped second HTTP stack
6. A8 README wrong on the security model
7. A6 no data layer
8. A7 test topology

### ADR candidates

- Route authorization derives from the module registry (A1), including how
  persona-scoped and role-scoped gates share one vocabulary.
- Provenance state of rendered data is a typed union, not a per-route convention (A5).
- The code-splitting boundary follows the authorization boundary (A4).

## Lens 1 — system design (`/system-design`)

### Frame

Pass 1 asked whether the structure is right. This pass asks what happens when
the system is under load, partly down, slow, or shared between people. The
console is a read-only browser client over a thin HTTP API and an agent server.
Its design work has gone into the READ CONTRACT and almost none into the
RUNTIME CONTRACT: what a request costs, when it stops, what is cached, what
survives, and how it is delivered.

### What holds

- **The truncation contract exists and is exemplary — in one place.** The NVL
  canvas declares NODE_CEILING = 300 as a constant, states in a comment that a
  canvas which silently shows part of the answer is worse than one that shows
  less and says so, tracks rowCount and nodeCount before the cap, and renders a
  TRUNCATED n/N badge. Two unit tests cover the capped and the uncapped case.
  This is the correct pattern and the rest of the console does not use it.
- **The failure-diagnosis probe (O85).** A failed fetch is followed by a
  no-cors probe that distinguishes a dead server from a blocked origin, and the
  message says what it observed rather than asserting a diagnosis. It closes a
  real defect where a wrong message sent readers to start a running server.
- **401 is terminal.** The authed client drops the session on 401 and the shell
  signs out everywhere via a window event, so expiry and revocation take effect.
  The earlier design silently re-logged-in and made rejection meaningless.
- **Params are fail-closed server-side.** Unknown keys rejected, required keys
  enforced, types checked, defaults applied, and the bound dict echoed back with
  the result. The client cannot smuggle a parameter the spec does not declare.
- **Export provenance is registered only on a completed stream.** A partially
  consumed export never registers a manifest, so no manifest describes a
  half-written file.

### S1 — The 500-row ceiling is invisible, and the button labelled "full" inherits it

Every QuerySpec in the registry carries the same optional parameter, limit,
default 500, applied inside the Cypher as LIMIT $limit. Roughly forty specs
share the single _LIMIT tuple.

No caller in web/ ever passes limit. Every runSpec call site sends either no
params or params unrelated to paging. There is no paging control anywhere in
the console — no offset, no cursor, no next-page, no AbortController.

So a spec whose true result is 900 rows returns 500, and the grid renders
`500/500 · drydocs · LIVE`. Nothing on screen distinguishes that from a
complete answer.

The sharp edge is the export. SpecGrid ships four export buttons. Two are
labelled `⬇ CSV (full)` and `⬇ JSONL (full)`, titled "Server export — re-runs
the spec, streams + manifest". That path calls `access.exportSpec(specId,
result.params, format)` — and `result.params` is the bound dict the server
echoed back, which already contains `limit: 500`. The server then re-applies
the same validation, streams exactly 500 rows, counts them, and registers a
provenance manifest with `row_count: 500`. The status line reports "exported
500 rows".

The result is a governance artifact — a manifest with a cypher_sha256, a
database, a classification and a trust tier — that faithfully records a
truncated extract and has no field saying so. There is no way for a console
user to obtain the other 400 rows, because no surface can raise the limit.

This is the same failure the canvas comment names, in the one place where the
output leaves the browser and gets filed.

Fix, cheapest first: (a) have the server return the pre-limit count, or run the
spec with `limit + 1` and report whether the extra row existed; (b) render the
same TRUNCATED badge the canvas already renders; (c) make the export path
either omit the display limit or record `truncated: true` and the ceiling in
the manifest. Until (c), the two buttons should not say "full".

### S2 — The session bearer token is forwarded into an agent transcript on another origin

The Ask spoke sends two message parts to the ADK server on port 8000. The
second is `controlPart(apiToken, apiUrl)`, which is
`{ text: JSON.stringify({ drydocs_control: { api_token, api_url } }) }`.

That is the console's live drydocs-api bearer token, placed inside a
conversation message, sent cross-origin to a server with no authentication of
its own, on every Ask turn. ADK persists sessions; a conversation part is
message content, and message content is the thing agent frameworks store,
replay, and log.

The handshake's purpose is legitimate — the agent registers ephemeral specs
owned by this session, and the R4 design needs the session identity to travel.
The objection is the CARRIER, not the requirement. A credential in a
transcript inherits the transcript's retention, its debug logging, and its
eventual export.

Two properties that limit the blast radius, stated so the finding is not
overweighted: the token is short-lived with a server-enforced expiry, and it
grants read access only. The exposure is a live read session, not a permanent
one.

Fix shapes: an Authorization header on the ADK call instead of a body part; or
a single-use exchange token minted for the agent with a short TTL and scoped to
ephemeral-spec registration; or the agent obtaining its own credential and the
console passing only a session id.

### S3 — There is no deployment shape

The API base URL is `import.meta.env.VITE_API_URL`, which Vite inlines at build
time. Consequences that follow directly:

- One build cannot be promoted across environments. Dev, staging and production
  each require their own `npm run build`, so the artifact that was tested is
  never the artifact that ships.
- The fallback is `'http://localhost:8001'`, hardcoded in twelve files. A
  production build with the variable unset points every user's browser at their
  own machine and shows them "nothing answered at http://localhost:8001 — start
  drydocs-api with: poetry run uvicorn ...". Nothing fails the build when the
  variable is missing.
- The same is true of `VITE_ADK_URL` defaulting to localhost:8000.

And nothing defines how the built console is served. There is no Dockerfile, no
nginx or Caddy config, no compose file, no static mount in drydocs_api — its
`static/` directory holds one dev demo HTML page. `dist/` is built by CI and
consumed by nothing.

That absence explains a cost the code already pays. Because nothing serves the
console and the API together, the console is cross-origin to its API in every
environment, which is why there is a CORS allowlist, an environment variable
to extend it, and a diagnostic probe to explain it. The reachability module
records that the documented verification port and the allowlist drifted apart
from O69 until 2026-08-30 with nobody noticing. Same-origin delivery — serving
`dist/` from the API, or a reverse proxy in front of both — removes the
allowlist, the probe's blocked-origin branch, and that class of drift.

ADR 0005 settled the ACCESS path. Nothing has settled the DELIVERY path, and
that is the larger open question of the two.

### S4 — Sign-out clears one storage key of eight

`signOut()` removes `drydocs.session.v2` and revokes the token server-side.
Everything else the console has written stays.

Eight distinct localStorage writers, only one of them versioned:

| what | keyed by | cleared on sign-out |
|---|---|---|
| session token | fixed key, v2 | yes |
| Ask last completed turn | per persona | no |
| app-code tray | per persona | no |
| onboarding progress | fixed | no |
| aside collapsed | fixed | no |
| theme | fixed | no |
| split-pane position | per module | no |
| grid column widths | per grid | no |

The first two matter. The Ask turn stores a completed envelope containing the
answer, the executed Cypher, per-step row counts and the task graph. The tray
stores selected application codes. Both are query results, both are keyed by
persona rather than by session, and both are readable after sign-out by whoever
opens the browser next — on a shared support desktop, that is a different
person. A console that renders an INTERNAL classification banner and a
not-for-redistribution notice over the same data on screen leaves it in
localStorage indefinitely.

`sessionRejected()` has the same gap, and it is the path taken when a session
expires while a tab is open.

Fix: one storage module owning a prefix, a version, and a `clearAll()` that
both sign-out paths call. Anything worth keeping across sign-outs (theme,
collapsed nav) opts out explicitly, which also makes the retention decision
visible rather than implicit.

### S5 — No timeouts, no cancellation, no retry, anywhere

An exhaustive search of `web/src` returns zero occurrences of AbortController
and zero request `signal:` options. The only setTimeout calls are a canvas fit
delay and a copy-confirmation reset.

- No request has a deadline. A slow Cypher, a saturated API, or a stalled TCP
  connection leaves the route in `data === null` forever, which every route
  renders as "Loading…". Loading and hung are the same screen.
- Nothing is cancelled. The cancelled-flag pattern in ~14 effects prevents a
  setState after unmount; it does not stop the request. Navigating away from a
  slow page leaves the work running.
- The Ask turn cannot be stopped. `runAgentSse` reads the stream to completion
  with no abort path, and the UI offers only `disabled={running}`. An agent that
  loops until its token budget is exhausted holds the surface for the whole run.
  For the one surface with genuinely unbounded latency, this is the one place a
  stop control is not optional.
- Nothing retries. That is a defensible choice for a read console and should be
  a stated one rather than an omission — particularly for a transient 502 from
  a restarting API, which currently drops the route to synthetic demo data
  (pass 1, A5).

### S6 — No caching, no shared fetch state, and no readiness signal

Each route builds its own GraphAccess with
`useMemo(() => createApiAccess(apiUrl, persona.id), [apiUrl, persona.id])`, and
each grid runs its spec in a `useEffect` keyed on `[access, specId]`. There is
no query cache, no store, no deduplication.

So: every navigation refetches, every tab switch refetches, browser back
refetches, and two panes on the same page needing the same spec run it twice.
Explorer to Ownership to Explorer is three full round trips for data that has
not changed. Read results with a declared classification and a stable
cypher_sha256 are close to the ideal cache candidate, and none of it is cached.

Related: `/health` exists in the API and is named in the client's own comment as
a public route, and nothing in `web/src` calls it. The console has no readiness
check, so "is the system up" is rediscovered independently by each route at the
moment it fails, and answered locally by falling back to demo data. One probe
at shell mount would let the whole console say "the API is down" once, instead
of eleven modules each deciding what to show.

### S7 — No error boundary: one render throw blanks the console

There is no ErrorBoundary and no componentDidCatch anywhere in `web/src`. React
19 unmounts the entire tree on an uncaught render error, so a single bad row —
an unexpected null where a string was indexed, a malformed generated artifact —
produces a white page with no navigation and no way back except a manual
reload.

This compounds with pass 1's A3 (strict mode off). Without strictNullChecks the
compiler is not enforcing the optional fields the generated types declare, so
the class of error most likely to reach render is exactly the class nothing
catches.

A boundary per route outlet, keyed on pathname so navigation clears it, is
about twenty lines and turns a blank console into one broken panel.

### S8 — Nothing observes the console in production

No telemetry, no client error reporting, no performance marks, no structured
logging. The only runtime signals are `console.*` calls and the status strings
each route renders for itself.

For most read-only UIs that is acceptable. It is not acceptable for this one,
because of the specific failure mode pass 1 identified: when the API is
unavailable, five routes substitute synthetic demo data behind a badge and keep
rendering. The application does not crash, does not error, and does not stop —
it quietly serves fabricated numbers. There is no signal anywhere that would
tell an operator this is happening, and the fallback is designed so the page
still looks healthy.

Also absent: any bundle-size budget in CI. The build job runs `npm run build`
and never asserts an output size, so the 3.68 MB chunk from pass 1 (A4) can
grow indefinitely without anything noticing.

The minimum worth having: count fallback activations, and fail CI on a bundle
size ceiling.

### Ranked

1. S1 the 500-row ceiling is invisible and the "full" export inherits it
2. S2 the session token rides inside an agent transcript
3. S3 no deployment shape (build-time URL, no artifact, localhost default)
4. S4 sign-out clears one storage key of eight
5. S5 no timeouts, no cancellation, no retry
6. S7 no error boundary
7. S6 no caching and no readiness signal
8. S8 nothing observes the console

### Cross-pass links

- S1 is the runtime face of pass 1's A5: the canvas solved provenance-of-
  completeness and the grid did not, the same way the canvas and the grid
  disagree about provenance-of-source.
- S3 is the delivery counterpart to A4: there is no code-splitting decision
  partly because there is no deployment decision to make one against.
- S7 depends on A3. A boundary is worth more when the compiler is not catching
  the nulls; strict mode is worth more when a throw does not blank the page.
- S6's missing cache is the same absence as A6's missing data layer, seen from
  the runtime side instead of the structural one.

### ADR candidates from this pass

- Result completeness is part of the read contract: every spec result carries
  whether it was capped, and no export may be labelled complete without it.
- The console's delivery shape: same-origin behind one server or proxy, with a
  runtime-configured API base rather than a build-time inlined one.
- Credential propagation to the agent tier: what carries session identity
  across the origin boundary, and what may never appear in a transcript.

## Lens 2 — technical debt (`/tech-debt`)

### Frame

Pass 1 asked whether the structure is right. Pass 2 asked what happens when the
system is under load or partly down. This pass asks what it costs to keep going,
and it is the pass where numbers replace judgement. Everything below was measured
on this tree, not inferred.

### What holds — and this part is unusual

- **Zero TODO, FIXME, XXX or HACK markers in 22,715 lines.** Not one.
- **Zero uses of `any`.** Not one, across 147 source files.
- **Lint exits 0.** Ten warnings, all cosmetic fast-refresh advice.
- **142 unit tests pass in 2.0 seconds.** No flake, no skips, no slow suite.
- **The comments carry rulings, not apologies.** Almost every non-obvious
  decision in lib/ names the item that made it and the failure it prevents.

This is not a sloppy codebase and it does not have the usual kind of debt. What it
has is debt that was chosen, mostly recorded, and never scheduled — plus a set of
measuring instruments that were installed and are not being read.

### T1 — Coverage is 7.51 percent, and the meter is installed but never read

Measured on this tree:

```
Statements   : 7.51%  (955 / 12,716)
Branches     : 70.49% (215 / 305)
Functions    : 52.69% (88 / 167)
```

The branch and function figures look healthy only because v8 counts branches
inside files a test actually loaded. Statements against all of src is the honest
number: 955 lines of 12,716 have ever executed under test.

Twelve test files against 147 source files. Zero in src/routes, which is where the
five largest hand-written files live. The e2e suite is one 75-line file with two
tests.

The part that makes this a tech-debt finding rather than a repeat of pass 1: the
package declares `@vitest/coverage-v8` as a devDependency, and there is **no
coverage script, no CI coverage step, and no threshold anywhere**. The instrument
was bought and has never been read. I had to invoke it by hand with explicit flags
to produce the numbers above.

A `test:coverage` script with a floor set at today's number, ratcheting upward,
costs one line of package.json and one CI step, and converts an unbounded slide
into a one-way gate.

### T2 — The one lint rule that catches real React bugs is off, and three files suppress it anyway

`.oxlintrc.json` enables exactly two rules: `react/rules-of-hooks` and
`react/only-export-components`. Beyond oxlint's own defaults, that is the whole
policy.

`react-hooks/exhaustive-deps` is not among them. And there is no ESLint in this
project at all — zero mentions in package.json, no binary in node_modules. So
these three lines suppress a rule that has never run:

- src/layout/useRouteA11y.ts:23
- src/routes/AdminConfigRoute.tsx:150
- src/routes/explorer/ExplorerRoute.tsx:87

They are template residue carried forward from the Vite starter. Each sits above a
genuine, deliberate, well-commented dependency omission — so the intent behind them
is sound and the mechanism behind them is fiction.

That matters more here than in most codebases, because the stale-closure shape is
everywhere: **14 hand-rolled `let cancelled = false` effects** and **16
`createApiAccess` memos**, all with hand-written dependency arrays, none checked by
anything.

Second, smaller point on the same config: lint currently emits 10 warnings and
exits 0, and the CI step runs `npm run lint` with no `--max-warnings 0`. Warnings
accumulate with no gate under them. Ten today.

### T3 — Twenty calls go over a wire the schema does not describe, and the mappings write surface is all of them

`unwrapAs` in lib/apiClient.ts is the most honest piece of debt tracking in the
repo. Its own comment says it plainly: every call site is a route
drydocs_api.schemas has not modelled yet, and the list of them is the follow-up

The concentration is the finding. O70's guarantee is that a server change the

This debt is named, mechanised and deliberately hard to grow. It still has no
closure date.

### T4 — The design tokens exist in three places, two of them frozen by hand

### T5 — Twenty-one double casts, all at the same seam

21 `as unknown as` casts. They cluster almost entirely at one boundary: a spec
result crossing into a typed row.

```
res.rows as unknown as LocationRow[]
r.rows as unknown as AppOption[]
grid?.rows ?? [] as unknown as OverrideGridRow[]
```

The double cast is required precisely because the two types do not overlap — the
single cast would be rejected. So the compiler is being switched off at exactly the
point where the server contract meets the render, in FileReport, LocationMap,
AppCodeCascadePane, IntakeRoute, LoadMapRoute, LoadsRoute, MappingsRoute and
SoftwareRoute.

Three findings meet here. Strict mode is off (A3), so nothing enforces the optional
fields inside the asserted shape either. There is no error boundary (S7), so a row
that does not match blanks the console rather than the panel. And the assertion is
a claim about server output that no test covers (T1).

One runtime row-shape validator at the seam would collapse all three into a
readable message.

### T7 — Five high-severity advisories, one root, none of them shipped

```
5 high severity vulnerabilities
@neo4j-nvl/base -> @segment/analytics-next
  effects: @neo4j-nvl/interaction-handlers, @neo4j-nvl/react
```

A graph visualization library pulling in a third-party analytics SDK. I checked

The debt is not the CVEs. It is that the count was recorded as **three** when O34

in the web CI job. A warn-only `npm audit --audit-level=high` step matches how the
parent repo already treats its lint-check-before-snapshot ritual: report, never
block.

### Three-pass summary

Across the three lenses, the same root shows up eight times: **a governing
abstraction exists, is correct, and the call sites route around it.**
canAccessModule with six inline predicates beside it (A1). apiBaseUrl with twelve

ceiling declared and rendered on the canvas, while the row ceiling next door is

exactly the discipline the parent repo already applies to its generated artifacts,
its module boundaries and its render parsing, and has not yet extended to web/.
