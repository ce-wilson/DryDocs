## Lens 1 — system design

Headline: **the load path does not truncate, and cannot prove it didn't.** The two
halves are one story — every default is honest, and none of that honesty reaches the
graph a consumer reads.

### L1-1 — a scoped or sampled load writes a `:JobRun` indistinguishable from a full one

`BaseLoader._open_run` (`drydocs/loaders/base.py:588`) opens the run node with exactly
six properties — `run_id`, `kind='load'`, `loader`, `source`, `started_at`, `status` —
and `_close_run` (`:606`) adds row counts and a final status. **No scope reaches it.**

The scope exists and is well built: `_scope_binds` (`drydocs/cli_shared.py:925-932`)
returns `folder_filter`, `run_as`, `developer_sid`, `row_cap`, `data_center_filter`,
`data_center_code`. Those are SQL binds and stop there. So a run that extracted a
1,000-row `--row-cap` sample of a ~240k-row table produces a run node identical in
shape to one that carried the population; only the row count differs, and a row count
cannot distinguish "a sample of a big table" from "a small table".

**Consequence, and it is the product thesis rather than a correctness bug.** DryDocs
exists to answer *what runs, what it depends on* — and a support engineer reading the
graph cannot tell whether the absence of a job means it does not exist or means the
load was scoped past it. The one lens question this module must answer well ("can a
consumer tell whether an answer came from the graph, a fixture, or a constant") is
answerable for SOURCE (`run.source`, set by every template from `$source_label`) and
not for COMPLETENESS.

**Where the scope does survive:** `caller_stamp()` (`drydocs_core/run_log.py:95`)
returns `"drydocs " + " ".join(sys.argv[1:])` into the run-log file's `script:` header,
so the invocation IS recorded — in a file, under `DRYDOCS_LOGDIR`, on the machine that
ran it. That is a real audit trail and it is not the graph.

**Cheapest correction:** one `SET` in `_open_run` carrying the non-null scope binds.
Deliberately NOT the raw `caller_stamp()` string: argv can carry `--run-as <FID>`, and
CLAUDE.md §3 keeps a tenant FID out of a publishable surface, so the correction records
the bind NAMES that were non-null plus the `row_cap` VALUE — enough to answer "was this
scoped?" without putting an identity in the graph. If that trade is contentious it is a
gate question (the scope property is new vocabulary), not a code change.

### L1-2 — the compounding half: the only record of scope is best-effort

`_open_run_log` (`base.py:393-399`) states its contract plainly: *"Best-effort by
contract: an unwritable log directory downgrades to a WARNING and the load proceeds
without a log — the audit trail is never the reason a load fails."*

That is the right call in isolation — a load should not fail because a log directory is
read-only. But combined with L1-1 it closes the loop the wrong way: the graph does not
carry the scope, the log does, and the log is allowed to be absent. **A capped load on a
machine with an unwritable `DRYDOCS_LOGDIR` leaves no record of its scope anywhere.**
Neither half is a defect alone; the pair is.

This is the same shape as the `web/` slot's top finding — a partial answer that reads
like a complete one — arriving by a different route, which is an argument for slot 10.

### L1-3 — what is genuinely clean, recorded so a later firing does not re-audit it

- **No default truncation anywhere in the load path.** `--row-cap` defaults to `None`
  (`cli_shared.py:989`, `typer.Option(None, ...)`) and the SQL documents `NULL =
  unlimited` (`sql/controlm_variables.sql:42`). Of 41 `.cypher` files, **zero** cap
  their writes; the two `LIMIT`/cap greps that fired are a prose "accepted limit" in
  `code_snapshot.cypher:15` and the documented `:row_cap` bind. Sampling is opt-in,
  named, and never the default.
- **The two invocation surfaces are deliberate and documented in place.**
  `LOADER_REGISTRY` (22 entries, 14 modules, `cli_shared.py:123`) is the ad-hoc `load`
  surface; `cli_ingest.py` imports a further 11 loader modules directly as their own
  verbs. `cli_shared.py:348-358` states the split and the reachability rule, so a reader
  who asks "is the registry the list of loaders?" is answered at the site rather than by
  inference. Not a finding.
- **A duplicate-preserving read is defended by a comment that cites its evidence**
  (`sql/controlm_variables.sql:57-60`): duplicate `(job, variable-name)` definitions are
  legitimate and observed, so the extract does not dedupe. That is the repo's rule about
  comments carrying rulings, working.
